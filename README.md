# Support Tickets — лабораторная по веб-архитектуре

Небольшая распределённая система обработки обращений. Здесь намеренно оставлены дефекты, похожие на реальные инциденты: задача лабораторной — пройти от пользовательского симптома до причины и исправления.

## Состав

```text
Browser → nginx → frontend
                → Tickets API → Event Service
                              → Slow Classification Service
```

- **Frontend** — готовый интерфейс. Его код считается корректным и не является частью задания.
- **Tickets API** — текущее состояние обращений, cache, authentication и бизнес-операции.
- **Event Service** — append-only история `ticket.created`, `ticket.status_changed`, `ticket.priority_changed`, `ticket.classified`.
- **Slow Classification Service** — определяет категорию обращения примерно за 20 секунд.
- Данные хранятся только в памяти и пропадают после перезапуска.

## Запуск

Нужны Docker и Docker Compose.

```bash
docker compose up --build
```

Открыть <http://localhost:8080>. API сервисов для диагностики доступны на портах `8000`, `8001`, `8002`; OpenAPI — по пути `/docs`.

> Первый запуск через nginx намеренно демонстрирует один из тикетов ниже. Это не ошибка Docker Compose.

Тестовый запуск без Docker:

```bash
python -m venv .venv
source .venv/bin/activate
pip install -e '.[test]'
pytest -q
```

## Пользователи

Frontend позволяет выбрать пользователя. Эквивалентные заголовки для ручных запросов:

| Пользователь | Роль | Заголовок |
|---|---|---|
| Alice | USER | `Authorization: Bearer alice-token` |
| Bob | USER | `Authorization: Bearer bob-token` |
| Support | SUPPORT | `Authorization: Bearer support-token` |
| Admin | ADMIN | `Authorization: Bearer admin-token` |

## API

```text
POST  /api/v1/tickets
GET   /api/v1/tickets
GET   /api/v1/tickets/{id}
PATCH /api/v1/tickets/{id}
PATCH /api/v1/tickets/{id}/status
GET   /api/v1/tickets/{id}/history
```

Пример создания:

```bash
curl -H 'Authorization: Bearer alice-token' \
  -H 'Content-Type: application/json' \
  -d '{"title":"Не проходит оплата","description":"Карта отклоняется","priority":"HIGH"}' \
  http://localhost:8000/api/v1/tickets
```

## Работа с лабораторной

1. Воспроизведите тикет только через описанный пользовательский flow.
2. Зафиксируйте ожидаемое и фактическое поведение.
3. Найдите слой, на котором возникает проблема.
4. Добавьте или исправьте тест, затем внесите минимальное исправление.
5. Убедитесь, что соседние сценарии не сломались.

Начните с `support-tickets/README.md`. Не изменяйте `frontend/`: интерфейс считается корректным. Тесты с пользовательскими сценариями находятся в `tests/`; часть из них ожидаемо помечена как `xfail`, пока соответствующий тикет не исправлен.

## Тикеты от поддержки

### SUP-101 — данные обращений не загружаются

После запуска интерфейс открывается, но список и любые действия с обращениями завершаются сообщением `502 Bad Gateway`. Контейнеры при этом выглядят запущенными.

### SUP-102 — иногда действия выполняются от другого пользователя

Если Alice и Bob почти одновременно активно работают с обращениями, в редких случаях запрос одного пользователя обрабатывается с данными другого. По одному запросу проблема почти не воспроизводится.

### SUP-103 — пользователи видят чужие обращения

Bob видит в списке обращение Alice и может открыть его по прямой ссылке.

### SUP-104 — автор обращения меняет статус

Обычный пользователь может перевести своё обращение в `CLOSED`, хотя это действие должно быть доступно только Support и Admin.

### SUP-105 — обращение принимает неизвестный приоритет

Форма API принимает значение `URGENT`, после чего интерфейс отображает непредусмотренный приоритет. Разрешены только `LOW`, `MEDIUM`, `HIGH`.

### SUP-106 — закрытое обращение нельзя отредактировать единообразно

Изменение закрытого обращения отклоняется раньше остальных правил и возвращает ответ в другом формате, чем аналогичные бизнес-ошибки.

### SUP-107 — изменение приоритета сохраняется, но запрос завершается ошибкой

Support меняет приоритет, получает ошибку, обновляет страницу и видит, что новое значение всё-таки сохранилось. В истории записи об изменении нет.

### SUP-108 — сервер перестаёт отвечать во время некоторых операций

Пока один пользователь создаёт обращение, другие запросы к тому же API могут надолго зависнуть.

### SUP-109 — создание обращения занимает около 20 секунд

Пользователь ждёт завершения дополнительной обработки, хотя категория не нужна для подтверждения создания обращения.

### SUP-110 — временный сбой зависимого сервиса долго удерживает запрос

При проблемах с дополнительными сервисами ответ приходит слишком поздно. Иногда повторяются запросы, которые повторять бессмысленно, а интервалы между попытками одинаковые.

### SUP-111 — двойной клик создаёт дубликаты

Два одинаковых запроса создания с одним `Idempotency-Key` создают два разных обращения.

### SUP-112 — после редактирования видны старые данные

Если сначала открыть обращение, затем изменить title или description и открыть его снова, некоторое время отображается прежняя версия.

### SUP-113 — текущее состояние и история расходятся

После части изменений карточка показывает новое значение, но timeline не содержит соответствующей записи.

## Критерии готовности исправленной версии

- nginx открывает frontend и проксирует `/api/`;
- USER видит только свои обращения, SUPPORT/ADMIN — все;
- статус меняют только SUPPORT/ADMIN;
- входные и бизнес-правила возвращают единообразные ответы;
- создание быстро возвращает ответ, классификация завершается отдельно;
- сетевые вызовы имеют осмысленные timeout/retry/backoff/jitter и не блокируют event loop;
- повторный `Idempotency-Key` не создаёт новый ticket;
- cache инвалидируется после изменений;
- история согласована с текущим состоянием либо сбой явно и безопасно обработан.
